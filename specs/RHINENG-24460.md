# Spec: RHINENG-24460

## Summary
Every GET /hosts request performs a SELECT COUNT(DISTINCT hosts.id) query with staleness OR conditions based on last_check_in timestamps, causing full sequential scans on the hosts table. In production, this takes 416ms for a 466K-host org and 83ms for a 23K-host org.

## Root Cause
In `api/host_query_db.py`, the function `_get_host_list_using_filters` always executes a COUNT(DISTINCT hosts.id) query via `count_total = filtered_query.with_entities(func.count(Host.id.distinct())).scalar()`. This is applied to a query that includes staleness filters generated by `app/staleness_states.py` (`HostStalenessStatesDbFilters`), which produce time-based OR conditions on `Host.last_check_in` (e.g., `now < last_check_in + stale_sec OR (last_check_in + stale_sec <= now < last_check_in + warn_sec)` etc.). Such compound OR conditions on arithmetic expressions over a timestamp column cannot be efficiently served by a btree index, causing PostgreSQL to fall back to a full sequential scan of all org hosts on every paginated request. The application already has Redis infrastructure (`api/cache.py`) used for staleness and system caches, but it is not yet utilized for the host count. The `pagination.yaml` schema currently requires `total` to be a non-nullable integer, meaning optional count (returning `null`) would also require schema changes.

## Affected Files
- `api/host_query_db.py`: Contains the `_get_host_list_using_filters` function with the expensive `func.count(Host.id.distinct())` call. This is the primary location where the optimization must be implemented — whether that means making the count optional (skipping it by default), using an estimated count via pg_class.reltuples, or caching the count result in Redis.
- `api/host.py`: Contains the `get_host_list` view function that calls `get_host_list_from_db`. If a `?count=true` query parameter approach is chosen, this file must be updated to accept and pass the new parameter down to the DB layer.
- `api/host_views.py`: Contains the views-endpoint host list handler that calls `get_host_list_for_views`. Similarly needs updating if the count optimization is extended to the views endpoint.
- `api/host_query.py`: Contains `build_paginated_host_list_response`, which builds the JSON response including `total`. If the optional-count approach is chosen and `total` can be `null`, this function needs to handle and pass through a `None` total value.
- `api/cache.py`: Already contains Redis client setup and staleness caching utilities. If the cached-count approach is chosen, new cache key helpers (e.g., `get_cached_host_count`, `set_cached_host_count`) following the existing pattern would be added here.
- `swagger/api.spec.yaml`: OpenAPI spec for the /hosts endpoint. Adding a `?count=true` query parameter requires adding it to the parameters list here. The `HostQueryOutput` schema extends `PaginationOut` which includes the `total` field — if `total` can be null, the schema also needs updating.
- `swagger/pagination.yaml`: Defines the `PaginationOut` schema and `Total` type, both of which currently require `total` as a required non-nullable integer. If the optional-count approach is adopted and `total: null` is returned when count is not requested, the `Total` schema must be made nullable and removed from the `required` list.
- `app/config.py`: Configuration file where new environment-variable-backed settings would be added, such as a count cache TTL, an org-size threshold for estimated-vs-exact count, or a feature flag to enable the optimization.
- `app/staleness_states.py`: Defines `HostStalenessStatesDbFilters` which generates the OR conditions on `Host.last_check_in` that make the COUNT query index-unfriendly. A longer-term fix (tracked in RHINENG-25499) involves removing or rewriting these timestamp-based staleness predicates to use index-friendly expressions.

## Behavioral Requirements

These requirements define the expected behavior independent of implementation approach. They should remain stable even if internal details (function signatures, line numbers, file structure) change.

1. **Default behavior: skip COUNT query.** GET /hosts and GET /beta/hosts-view requests that omit the `count` parameter (or set it to `false`) must NOT execute a COUNT(DISTINCT hosts.id) query. The response must include `"total": null` in the pagination metadata.
2. **Opt-in exact count.** When the caller passes `?count=true`, the response must include `"total": <integer>` with the exact count of matching hosts. The COUNT query is only executed in this case.
3. **Schema compatibility.** The `total` field in pagination responses must accept both `integer` and `null` values. It must not be marked as required in the response schema.
4. **ID-list endpoints unaffected.** GET /hosts/{host_id_list} must continue to always compute and return an accurate integer `total`, since downstream logic (`check_all_ids_found`) depends on it.
5. **Invalid parameter handling.** An invalid value for the `count` query parameter (e.g., `count=banana`) must return HTTP 400.
6. **Backward-compatible pagination.** When `count=true` is passed and the count is zero, the endpoint should still return an empty host list with `total: 0` (preserving the existing early-return optimization). When count is not requested, the paginated query runs regardless and returns an empty list naturally if no hosts match.

## Implementation Plan

> **Note:** The steps below describe one proposed implementation approach. Specific function signatures, line numbers, and test names are illustrative and may shift as the codebase evolves. The [Behavioral Requirements](#behavioral-requirements) above are the authoritative contract.

### Step 1: Make `total` optional and nullable in the pagination schema. In the `PaginationOut` schema, remove `total` from the `required` list. In the `Total` schema, add `nullable: true` so that `null` is a valid value when the count is not computed.
- File: `swagger/pagination.yaml`
- Change type: modify
- Rationale: The API will now return `total: null` by default (when the expensive COUNT query is skipped). This schema change allows consumers to receive a null total without a validation error. Removing `total` from `required` and making it nullable is the minimal change needed to support the optional count feature.

### Step 2: Add a `countParam` query parameter definition to `components/parameters` section. It should be: `name: count, in: query, required: false, schema: {type: boolean, default: false}, description: 'When true, executes a COUNT(DISTINCT hosts.id) query and returns total; omit or set false to skip the count and return total: null.'`. Then reference `$ref: '#/components/parameters/countParam'` in the GET /hosts and GET /beta/hosts-view parameters lists.
- File: `swagger/api.spec.yaml`
- Change type: modify
- Rationale: Connexion auto-generates function signatures from the OpenAPI spec. Adding this parameter to the spec makes it available as a `count` kwarg in the view functions. Adding it to both /hosts and /beta/hosts-view ensures the optimization is applied to both endpoints.

### Step 3: Make the COUNT query conditional in the DB layer.

Add a `compute_count` boolean parameter (default `True`) to `_get_host_list_using_filters`, `get_host_list`, and `get_host_list_for_views`. Update return type annotations to allow `int | None` for the count value.

**`compute_count=True` path (explicit count requested):**
1. Execute the COUNT query: `count_total = filtered_query.with_entities(func.count(Host.id.distinct())).scalar()`
2. If `count_total == 0`, early-return with `([], 0, additional_fields, system_profile_fields)` — this preserves the existing optimization that skips the paginated query when no rows match.
3. Otherwise, proceed to the paginated query and return `count_total` as the total.

**`compute_count=False` path (default, count skipped):**
1. Set `count_total = None` — no COUNT query is executed at all.
2. Skip the early-return zero-check (since we don't know the count).
3. Proceed directly to the paginated query, which will naturally return an empty list if no rows match.
4. Return `None` as the total.

Note: `get_host_list_by_id_list` does NOT receive the `compute_count` parameter because it always needs an accurate count for `check_all_ids_found` validation.

- File: `api/host_query_db.py`
- Change type: modify
- Rationale: This is the core change that eliminates the expensive SELECT COUNT(DISTINCT hosts.id) query on every GET /hosts request by default. Using `compute_count=True` as default keeps the signature backward-compatible for `get_host_list_by_id_list` which must always compute count. When `compute_count=False`, only the paginated SELECT runs — no COUNT query — saving 83–416ms per request.

### Step 4: In the `get_host_list` view function, add `count=False` to its parameter list (connexion will inject this from the spec). Then pass `compute_count=count` (or `compute_count=bool(count)`) as a keyword argument to `get_host_list_from_db(...)` call. No other logic in the function needs to change since `build_paginated_host_list_response` already accepts and passes through a `None` total.
- File: `api/host.py`
- Change type: modify
- Rationale: The view function is the entry point that bridges the HTTP parameter from connexion to the DB layer. Adding `count=False` here means callers that omit `?count` get the fast no-count path, while callers that pass `?count=true` get the exact total.

### Step 5: In the `get_host_views` view function, add `count=False` to its parameter list. Pass `compute_count=count` to `get_host_list_for_views(...)`. In `_build_host_view_response`, the `total` value is already used as `"total": total` in the response dict, so it already handles `None` naturally.
- File: `api/host_views.py`
- Change type: modify
- Rationale: The /beta/hosts-view endpoint has the same performance issue — it also calls `_get_host_list_using_filters` under the hood. Applying the same optimization here ensures consistency across both endpoints.

### Step 6: Two changes: (1) Update `api_per_page_test` to accept an `extra_query_params=None` keyword argument and merge it into the `query_parameters` dict passed to `api_get` (e.g., `params = {"page": page, "per_page": per_page, **(extra_query_params or {})}`). (2) Propagate `extra_query_params` through `api_base_pagination_test` and `api_pagination_test` signatures so callers can pass it. (3) Update `assert_paginated_response_counts` to conditionally skip the `assert response_data["total"] == expected_total` line when `response_data["total"] is None`, so new no-count tests do not fail this assertion.
- File: `tests/helpers/api_utils.py`
- Change type: modify
- Rationale: Without these helper changes, all 20+ existing tests in test_api_hosts_get.py that call `api_pagination_test` will fail because they don't pass `count=true` and will receive `total: null` instead of an integer. Adding `extra_query_params` support lets existing host-list tests opt into `count=True` without rewriting every test individually.

### Step 7: Two types of changes: (1) Add two new test functions: `test_get_host_list_omitting_count_returns_null_total` — creates a host, calls GET /hosts without `?count`, asserts `response_status == 200` and `response_data["total"] is None`; and `test_get_host_list_with_count_true_returns_integer_total` — creates hosts, calls GET /hosts with `?count=true`, asserts `response_data["total"]` is an integer equal to the number of created hosts. (2) Update all existing `api_pagination_test(api_get, subtests, url, ...)` and `api_base_pagination_test(api_get, subtests, url, ...)` calls that use host list URLs to pass `extra_query_params={"count": True}` so those tests still exercise and verify the total count path.
- File: `tests/test_api_hosts_get.py`
- Change type: modify
- Rationale: The new tests directly verify the fix — that the COUNT query is skipped by default and executes only when explicitly requested. Updating existing pagination test calls with `extra_query_params={"count": True}` ensures backward-compatible test coverage for the total count field without modifying every individual test body.

## Test Strategy
- Approach: Unit/integration tests using the existing pytest + Flask test client pattern. New tests verify the two behavioral cases: (a) default request returns null total without hitting the COUNT query, and (b) explicit count=true request returns an accurate integer total. Existing pagination tests are updated to pass count=true so they continue to verify total-count correctness. Optionally, a mock/patch on `_get_host_list_using_filters` can assert that `func.count` is NOT called when `compute_count=False`.
- Test files: tests/test_api_hosts_get.py, tests/helpers/api_utils.py
- Coverage targets: GET /hosts with no `count` param returns HTTP 200 with `total: null` in response body, GET /hosts?count=true returns HTTP 200 with `total` as a non-negative integer equal to the number of matching hosts, GET /beta/hosts-view with no `count` param returns `total: null`, GET /beta/hosts-view?count=true returns integer `total`, Existing host list pagination tests continue to verify correct total when `count=true` is passed, GET /hosts/{id_list} (get_host_by_id) is unaffected — still returns integer total (no change to get_host_list_by_id_list), Invalid `count` parameter value (e.g., `count=banana`) returns HTTP 400

## Risk Notes
- BREAKING CHANGE for API consumers that currently parse `total` as a guaranteed integer: they will receive `null` after this change unless they add `?count=true`. Coordinate with HCC UI and other consumers before deploying.
- The early-exit optimization `if count_total == 0: return [], 0, ...` must be carefully preserved for the compute_count=True path and safely removed/bypassed for the compute_count=False path. When count is skipped, the paginated query must still run even when there are zero matching hosts; SQLAlchemy's `paginate(error_out=True)` will naturally return an empty list in that case.
- connexion may pass `count` as a Python bool (`True`/`False`) or as a string depending on how the spec defines it. Ensure the spec uses `type: boolean` and the Python code treats the param as a boolean (or uses `bool(count)`).
- The `api_pagination_index_test` helper also calls `api_get` with only `page` and `per_page` params and does not assert on `total`, so it is safe without changes. However `assert_paginated_response_counts` called within `api_base_pagination_test` DOES assert on `total`, hence the helper update is required.
- OpenAPI nullable handling: In OpenAPI 3.0, `nullable: true` must be added to the `Total` schema directly. In OpenAPI 3.1 this would be `type: [integer, 'null']`. Since the spec is 3.0 (as declared in api.spec.yaml), use `nullable: true`.
- The `get_host_list_by_id_list` function signature is unchanged (no `compute_count` param) since it always needs an accurate total for `check_all_ids_found` to work correctly. Verify this function is not accidentally affected.
- Redis caching of count (mentioned as follow-on in the analysis) is out of scope for this ticket. The plan only implements the opt-in exact-count path.
- Staleness filters from `app/staleness_states.py` still produce time-based OR conditions on `last_check_in`. The count-skipping approach eliminates the COUNT query overhead but the staleness predicates are still applied to the paginated SELECT. The RHINENG-25499 prerequisite (removing staleness timestamps) would further improve the paginated query itself.

## Constraints
- The Jira comments note that RHINENG-25499 (removing staleness timestamps) is a prerequisite for the most impactful optimization; this ticket was blocked pending that work.
- The `total` field in API responses is currently required and non-nullable per `swagger/pagination.yaml`. Making it nullable is a breaking API change that requires coordination with UI consumers (HCC) and other API consumers.
- The application already has Redis infrastructure; however, cached counts would be eventually consistent (30–60s stale). This may not be acceptable for use cases that rely on accurate counts for pagination correctness.
- If estimated counts (pg_class.reltuples) are used, they may be significantly off after bulk inserts/deletes (up to ~5% inaccuracy), which could cause pagination to generate incorrect last-page offsets.
- The `get_host_list_by_id_list` function also calls `_get_host_list_using_filters` and would be affected by any changes to that function's signature.
- Any new `?count` query parameter must be added to the OpenAPI spec and validated through the connexion framework, which auto-generates function signatures from the spec.
- Production Redis is already used for staleness and system caches; adding a count cache must account for key namespace collisions and appropriate TTL tuning.
