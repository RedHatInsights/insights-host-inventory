# Spec: RHINENG-24460

## Summary
Every GET /hosts request executes a SELECT COUNT(DISTINCT hosts.id) query with staleness OR-range conditions that force a full sequential scan of all hosts per org, causing significant latency (416ms for 466K-host orgs, 83ms for 23K-host orgs). The task is to optimize or make this COUNT optional.

## Root Cause
In `api/host_query_db.py`, the function `_get_host_list_using_filters` unconditionally executes `filtered_query.with_entities(func.count(Host.id.distinct())).scalar()` (line 159) on every paginated host-list request. The `all_filters` passed into this query always include staleness conditions generated by `HostStalenessStatesDbFilters` in `app/staleness_states.py`, which produce OR-combined range predicates on the `Host.last_check_in` column (e.g., `now < last_check_in + stale_sec OR (now >= last_check_in + stale_sec AND now < last_check_in + warn_sec) ...`). PostgreSQL cannot efficiently use a B-tree index to serve these nested OR-range conditions, so it falls back to a sequential scan of the entire `hosts` table filtered by `org_id`. Because `total` is always included in the API response (enforced by `build_paginated_host_list_response` in `api/host_query.py` and the pagination schema in `swagger/pagination.yaml`), this expensive COUNT is issued on every single GET /hosts call. The four approach options discussed in the ticket (optional count via `?count=true`, estimated count via `pg_class.reltuples`, Redis-cached count, or a combination) all address this by either eliminating or approximating the COUNT query.

## Affected Files
- `api/host_query_db.py`: Contains `_get_host_list_using_filters`, which is the single location where `func.count(Host.id.distinct())` is executed unconditionally. This is where the count logic must be modified — either made conditional on a parameter, replaced with an estimate, or cached.
- `api/host_query.py`: Contains `build_paginated_host_list_response`, which always serializes `total` into the response dict. If the chosen approach is to make count optional (returning `null` when not requested), this function needs to accept and forward a nullable `total`.
- `api/host.py`: Contains the `get_host_list` view (GET /hosts). If a `?count=true` query parameter approach is chosen, the parameter must be declared here and threaded through to the DB layer. Also calls `build_paginated_host_list_response`.
- `api/host_views.py`: Contains the `get_host_views` view (GET /beta/hosts-view), which also calls `get_host_list_for_views` → `_get_host_list_using_filters`. Same COUNT issue applies to this endpoint.
- `api/host_group.py`: Contains `get_host_list_by_group`, which calls the shared `get_host_list` DB function; also affected by the same slow COUNT path via `_get_host_list_using_filters`.
- `swagger/api.spec.yaml`: The OpenAPI spec for GET /hosts. If a `?count=true` query parameter or any other API-visible change is introduced, this spec file must be updated to declare the new parameter.
- `swagger/pagination.yaml`: Defines the `PaginationOut` schema including `total` as a required integer. If `total` becomes nullable (returned as `null` when count is not requested), this schema must be relaxed to allow `nullable: true`.
- `app/staleness_states.py`: Defines `HostStalenessStatesDbFilters`, which produces the index-unfriendly OR-range conditions on `Host.last_check_in` that make the COUNT query slow. Understanding this file is critical to evaluating whether the filter structure can itself be changed (e.g., as part of the linked RHINENG-25499 ticket which targets staleness timestamp removal).

## Implementation Plan

### Step 1: 1. Add a `count: bool = False` parameter to `_get_host_list_using_filters`. When `count=False`, skip the `filtered_query.with_entities(func.count(Host.id.distinct())).scalar()` call entirely and skip the `count_total == 0` early-exit guard (the paginate call still handles empty results correctly via error_out). Return `None` as the total in this case. When `count=True`, execute the COUNT as today and use the existing early-exit.
2. Add `count: bool = False` to the public `get_host_list` function signature and pass it through to `_get_host_list_using_filters`.
3. Update the `get_host_list_for_views` function similarly — add `count: bool = False` and pass to `_get_host_list_using_filters`.
4. Update `get_host_list_by_id_list` similarly for consistency.

Concrete diff for `_get_host_list_using_filters`:
- Change signature: `def _get_host_list_using_filters(..., count: bool = False) -> tuple[list[Host], int | None, ...]:`
- Replace the unconditional COUNT block with:
  ```python
  if count:
      count_total = filtered_query.with_entities(func.count(Host.id.distinct())).scalar()
      if count_total == 0:
          return [], 0, additional_fields, system_profile_fields
  else:
      count_total = None
  ```
- File: `api/host_query_db.py`
- Change type: modify
- Rationale: This is the single location that executes the expensive COUNT query on every GET /hosts request. Making it conditional (off by default) eliminates the full sequential scan for the common case where callers do not request a count.

### Step 2: Update `build_paginated_host_list_response` to accept a nullable `total`. Change the `total` parameter type annotation to `int | None` and update the returned dict so `'total': total` passes through `None` unchanged (no other logic change needed — Python serializes `None` as JSON `null` automatically).
- File: `api/host_query.py`
- Change type: modify
- Rationale: The response builder must not coerce `None` total to an integer. Allowing `None` lets the JSON response include `"total": null` when the count was skipped.

### Step 3: Add `count=False` as a keyword argument to the `get_host_list` view function (connexion maps query parameters by name). Pass `count` down to `get_host_list_from_db(..., count=count)`. The cached fast-path branch (insights-client system query) already hardcodes `total=1` and is unaffected.
- File: `api/host.py`
- Change type: modify
- Rationale: The view function is where connexion injects query parameters. Declaring `count` here causes connexion to parse `?count=true` / `?count=false` from the HTTP request and route it to the DB layer.

### Step 4: Two changes:
1. Add a reusable `countParam` entry under `components/parameters`:
   ```yaml
   countParam:
     name: count
     in: query
     required: false
     schema:
       type: boolean
       default: false
     description: >-
       When true, include the total host count in the response.
       Omitting or setting to false skips the COUNT query for better performance
       and returns null for the total field.
   ```
2. Add `- $ref: '#/components/parameters/countParam'` to the parameter list of the `GET /hosts` operation (line ~50 in the spec).
- File: `swagger/api.spec.yaml`
- Change type: modify
- Rationale: The OpenAPI spec drives connexion parameter parsing. Without declaring `count` here, connexion will not inject it into the view function and will reject or ignore it.

### Step 5: Make the `total` field nullable in the `PaginationOut` schema and in the `Total` component schema:
1. On the `Total` schema add `nullable: true`.
2. Keep `total` in the `required` list of `PaginationOut` (the field is always present, but may be `null`).

Result:
```yaml
Total:
  type: integer
  nullable: true
  description: Total number of items
```
- File: `swagger/pagination.yaml`
- Change type: modify
- Rationale: Existing consumers parse `total` as a required field. Keeping it required but nullable means the field is always present (no missing-key errors) while allowing `null` when the count was skipped. This is the least-breaking schema change.

### Step 6: Add two new test functions:
1. `test_get_host_list_default_total_is_null` — create a few hosts, call `GET /hosts` without any `count` parameter, assert response status 200 and that `response_data['total'] is None`.
2. `test_get_host_list_count_true_returns_integer_total` — create a few hosts, call `GET /hosts?count=true`, assert response status 200 and that `response_data['total']` equals the expected integer count.

Also add a brief unit test (can be in the same file or a new `tests/test_host_query_db.py`) that mocks `filtered_query.with_entities(...).scalar()` and verifies it is NOT called when `count=False` is passed to `_get_host_list_using_filters`.
- File: `tests/test_api_hosts_get.py`
- Change type: modify
- Rationale: These tests directly verify the two code paths introduced by the fix: (a) COUNT is skipped and null is returned by default, and (b) COUNT is executed and an integer is returned when explicitly requested.

## Test Strategy
- Approach: Integration tests via the existing Flask test client (api_get fixture). Unit-level mock test for the DB layer to assert the COUNT query is not issued when count=False.
- Test files: tests/test_api_hosts_get.py
- Coverage targets: GET /hosts (no count param) returns HTTP 200 with total=null, GET /hosts?count=false returns HTTP 200 with total=null, GET /hosts?count=true returns HTTP 200 with total equal to the actual host count, func.count(Host.id.distinct()) is NOT called when count=False in _get_host_list_using_filters, func.count(Host.id.distinct()) IS called when count=True in _get_host_list_using_filters, Pagination still works correctly (correct results, correct page/per_page in response) when total=null

## Risk Notes
- Breaking change for existing API consumers: `total` will now be `null` by default instead of an integer. Any UI or client that does arithmetic on `total` without a null-check will break. Coordinate with consumers before deploying.
- The `count_total == 0` early-exit optimization is lost when count=False. For orgs with zero matching hosts the query will proceed to paginate() and return an empty list — this is correct but one extra DB round-trip.
- Flask-SQLAlchemy paginate() with error_out=True raises 404 when page > 1 and results are empty. This behavior is unchanged, but without a count we cannot proactively catch out-of-bounds page numbers before hitting the DB.
- host_group.py (GET /groups/{group_id}/hosts) and host_views.py (GET /beta/hosts-view) call _get_host_list_using_filters indirectly. Because the new default is count=False, they will automatically skip the COUNT query without needing API-level changes. If those endpoints need count=true support, their swagger specs and view functions must be updated in a follow-up.
- The cached fast-path in api/host.py (insights-client system queries) hardcodes total=1 and is unaffected by this change.
- Once RHINENG-25499 (staleness timestamp removal) lands, re-evaluate enabling count=True by default and adding a B-tree index on (org_id, last_check_in) to make exact counts cheap again.

## Constraints
- The `total` field is currently a required field in `PaginationOut` (swagger/pagination.yaml) and existing UI consumers rely on it for pagination rendering. Any approach that removes or makes `total` nullable is a breaking API change that must be coordinated with consumers.
- The Jira comments note that removing staleness timestamps (RHINENG-25499) is a prerequisite for the most impactful index optimization. Until those timestamps are removed, the COUNT query will remain slow even if other optimizations are applied.
- An estimated count approach (pg_class.reltuples) is fast but approximate (~95% accuracy). It would be incorrect for small orgs or immediately after bulk imports/deletes. A threshold-based switch (e.g., >10K hosts use estimate) reduces the accuracy risk.
- A Redis-cached count introduces an external dependency and adds TTL-based eventual consistency. Cache invalidation on host create/delete events would be needed to avoid stale counts.
- The `get_host_list_by_id_list` function also calls `_get_host_list_using_filters`; any signature change to that internal function must be propagated consistently.
- Pagination correctness must be preserved: the `error_out=True` in `paginate()` depends on `count_total` to validate page bounds. If count is omitted, the early-exit on `count_total == 0` and page validation logic must be revisited.
