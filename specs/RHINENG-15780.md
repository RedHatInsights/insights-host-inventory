# Spec: RHINENG-15780

## Summary
Optimize staleness query filters by combining consecutive staleness states into simpler, single-range SQL conditions.

## Root Cause
When filtering hosts by multiple staleness states (e.g., fresh, stale, stale_warning), the system builds an OR-conjunction of individual state filters. Each individual filter uses timestamp comparisons against boundaries (e.g., stale_boundary, stale_warning_boundary, deletion_boundary). When consecutive states are requested, these individual filters overlap at their boundaries, resulting in redundant and complex SQL conditions (e.g., `now < stale_boundary OR (now >= stale_boundary AND now < stale_warning_boundary) OR ...`). These can be simplified into a single range check (e.g., `now < deletion_boundary` if all three non-culled states are requested).

## Plan

- `app/staleness_states.py` (modify): Add a `combined_filter(states)` method to `HostStalenessStatesDbFilters` that accepts a list of state names and returns an optimized SQLAlchemy filter expression. The method should identify consecutive runs of states in the canonical order (fresh → stale → stale_warning → culled) and merge each run into a single range condition using only the outer boundaries. For example, a run of [fresh, stale] becomes a single `now < stale_warning_boundary`, a run of [stale, stale_warning] becomes `now >= stale_boundary AND now < deletion_boundary`, and [fresh, stale, stale_warning] becomes `now < deletion_boundary`. Non-consecutive states are kept as separate conditions and OR'd together. **Important**: when all four states are requested (a complete run covering fresh through culled), the combined filter must NOT simplify to an unconditional match. Instead, it must still require that `last_check_in` (or `modified_on`) `IS NOT NULL`, preserving the existing behavior that excludes hosts with no check-in timestamp.

- `api/filtering/db_filters.py` (modify):
  - Update `_staleness_filter` to call the new `combined_filter` method on `HostStalenessStatesDbFilters` instead of iterating over individual states with `getattr` and OR'ing them. The `["unknown"]` special case should remain unchanged. Additionally, when the input list contains `unknown` mixed with recognized states (e.g., `["fresh", "unknown", "stale"]`), `_staleness_filter` must strip `unknown` from the list before passing the remaining recognized states to `combined_filter`, and handle the `unknown` filter separately (OR'd with the combined result). This preserves the existing behavior where `unknown` is only handled as a special case and never passed into the staleness-state logic.
  - Update `staleness_to_conditions` to optimize consecutive staleness states. Instead of yielding a condition for each individual state, it should identify consecutive runs of standard states (`fresh`, `stale`, `stale_warning`, `culled`) in the canonical order and merge each run into a single range `(gt, lte)` condition.
    - For a consecutive run, the merged range's `gt` is the `gt` of the oldest state in the run (or `None` if `culled` is in the run), and the `lte` is the `lte` of the newest state in the run (or `None` if `fresh` is in the run).
    - Non-consecutive states or other states (like `not_culled`) are kept as separate conditions.
    - This optimization automatically benefits the `per_reporter_staleness_filter` path and other queries using `staleness_to_conditions` (such as host reaper jobs), ensuring consistent logic across all staleness filters.

- `tests/culling/test_custom_staleness.py` (modify):
  - Add tests for the optimized combined staleness filter. Tests should cover: (1) consecutive pair [fresh, stale] matches a host in the fresh window and a host in the stale window but not stale_warning or culled; (2) consecutive pair [stale, stale_warning] matches hosts in those windows but not fresh or culled; (3) all three non-culled states [fresh, stale, stale_warning] matches any non-culled host; (4) non-consecutive states like [fresh, stale_warning] correctly match fresh and stale_warning hosts but not stale or culled hosts; (5) all four states [fresh, stale, stale_warning, culled] match any host that has a non-NULL `last_check_in`/`modified_on`, but exclude hosts with NULL values (preserving existing behavior); (6) mixed inputs containing `unknown` alongside recognized states (e.g., `["fresh", "unknown"]`) correctly handle `unknown` separately and do not pass it to `combined_filter`; (7) the singleton `["unknown"]` case continues to work as before. Use the existing `db_create_host` fixture and set `last_check_in` to place hosts into specific staleness windows, following the pattern of existing tests like `test_staleness_db_filter_fresh_uses_org_defaults_when_columns_null`.
  - Add tests for the optimized `staleness_to_conditions` and `per_reporter_staleness_filter` paths. These tests should verify that consecutive states (e.g., `["fresh", "stale"]`, `["stale", "stale_warning"]`, `["fresh", "stale", "stale_warning"]`) are correctly merged into a single range condition and yield the expected query results, matching the behavior of the main staleness filter optimization.

## Constraints
- The optimization must preserve exact logical semantics — no host should be included or excluded differently than before
- The optimization must be applied consistently across all staleness filters, including the main staleness filter, `per_reporter_staleness_filter`, and `staleness_to_conditions` paths.
