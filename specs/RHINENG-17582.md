# Spec: RHINENG-17582

## Summary
Handle database deadlocks gracefully when deleting hosts closely after changing staleness settings.

## Root Cause
When deleting custom staleness settings and then deleting a host immediately, concurrent database transactions (possibly from background workers, other requests, or event listeners) can cause a deadlock on the hosts table. This results in a 500 OperationalError.

## Plan

- `api/host.py` (modify): Import `OperationalError` from `sqlalchemy.exc`, `OutboxSaveException` from `app.exceptions`, `is_deadlock_error` from `lib.db`, and `time` from the standard library. Define a module-level constant `DEADLOCK_MAX_RETRIES = 3` and `DEADLOCK_RETRY_DELAY = 0.5` (seconds). In `_delete_host_list`, initialize accumulators for `hosts_deleted` count and tracking data (e.g., `deleted_ids_accumulated` list) before the retry loop so that committed progress from earlier attempts is preserved across retries. Wrap the `delete_hosts` call and its result consumption (the list comprehension iterating over `result_list` and the subsequent tracking loop) in a retry loop. The loop runs up to `DEADLOCK_MAX_RETRIES` attempts. On each attempt, catch both `OperationalError` and `OutboxSaveException`. For `OperationalError`, check via `is_deadlock_error(e)`. For `OutboxSaveException`, check if the underlying cause is a deadlock via `is_deadlock_error(e.__cause__)` (since `write_events_to_outbox_batch` wraps `SQLAlchemyError` in `OutboxSaveException` using `raise ... from db_error`). When the caught error is a deadlock, log a warning including the attempt number, call `db.session.rollback()` to release locks, sleep for `DEADLOCK_RETRY_DELAY` seconds, and continue to the next attempt — the accumulators retain the count and IDs from any batches that committed before the deadlock so that `hosts_deleted` is not undercounted. If all retry attempts are exhausted, log a final warning and call `flask.abort(409)` with a message indicating a concurrent operation conflict and advising the client to retry later. Re-raise non-deadlock errors unchanged on any attempt. Because the handler is inside `_delete_host_list`, it covers all three calling paths: `delete_host_by_id`, `delete_hosts_by_filter`, and `delete_all_hosts`.

- `tests/test_api_hosts_delete_by_id.py` (modify): Add a test that creates a host, then patches `api.host.delete_hosts` to raise an `OperationalError` wrapping a `psycopg2.errors.DeadlockDetected` (construct as `OperationalError("deadlock detected", params=None, orig=DeadlockDetected())`). The mock should raise on every call so that all retry attempts fail. Verify the API returns a 409 status. Model the test after the existing `test_attempt_delete_host_read_only` test which patches a dependency and asserts a non-200 response code. Import `OperationalError` from `sqlalchemy.exc` and `DeadlockDetected` from `psycopg2.errors`. Add a second test where the mock raises `OutboxSaveException` with a `DeadlockDetected`-caused `OperationalError` as its `__cause__` on every call, and verify the API also returns 409. Add a third (recovery) test where the mock raises an `OperationalError` wrapping `DeadlockDetected` on the first call but succeeds on the second call, and verify the API returns a 200 status — confirming that the retry mechanism works end-to-end. Also mock `time.sleep` in the deadlock tests to avoid actual delays.

## Constraints
- The delete operation must be retried up to 3 times before returning a 409. Each retry should roll back the failed session and wait briefly to allow the conflicting transaction to complete.
- Non-deadlock `OperationalError` instances must still propagate as 500 errors — only DeadlockDetected should be converted to 409.
- Non-deadlock `OutboxSaveException` instances must also propagate unchanged.

## Known Limitations (out of scope for this fix)
- **Message ordering with rollback**: If a deadlock occurs after deletion events have already been published to Kafka (e.g., during a later batch's flush/commit), consumers may receive deletion events for hosts that were not actually deleted because the transaction rolled back. A full fix would require a transactional outbox pattern or post-commit message publishing, which is a larger architectural change. This should be tracked as a follow-up item.
- **Partial batch deletion retries**: When `delete_hosts` processes hosts in batches and a later batch deadlocks after earlier batches have already committed, the accumulators preserve counts from committed batches, but the 409 response does not report which hosts were successfully deleted. A subsequent retry of the same ID list by the client may fail `check_all_ids_found` for already-deleted hosts. A full fix would require returning partial progress in the 409 response body. This should also be tracked as a follow-up item.
