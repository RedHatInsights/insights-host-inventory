# Spec: RHINENG-17582

## Summary
Handle database deadlocks gracefully when deleting hosts closely after changing staleness settings.

## Root Cause
When deleting custom staleness settings and then deleting a host immediately, concurrent database transactions (possibly from background workers, other requests, or event listeners) can cause a deadlock on the hosts table. This results in a 500 OperationalError.

## Plan

- `api/host.py` (modify): Import `OperationalError` from `sqlalchemy.exc`, `OutboxSaveException` from `app.exceptions`, `is_deadlock_error` from `lib.db`, and `time` from the standard library. Define a module-level constant `DEADLOCK_MAX_RETRIES = 3` and `DEADLOCK_RETRY_DELAY = 0.5` (seconds). In `_delete_host_list`, wrap **only** the `delete_hosts` call and its result consumption in a retry loop that runs up to `DEADLOCK_MAX_RETRIES` attempts. The tracking loop (`for host_id in host_id_list`) must remain **outside and after** the retry loop. Initialize a `set` (`deleted_id_set`) **once before the retry loop** to accumulate unique IDs across attempts. Inside the retry loop, replace the list comprehension `[str(r.row.id) for r in result_list]` with an explicit `for` loop that adds each ID to `deleted_id_set` individually. This avoids the list comprehension discarding partial results on exception. Note that `delete_hosts` is a generator that yields results from each batch **before** `session_guard` exits and commits that batch's transaction. If a deadlock occurs during `session_guard`'s commit phase, the batch is rolled back by `session_guard`, but any IDs yielded from that batch have already been added to `deleted_id_set`. Those rolled-back IDs will still exist in the database and will be picked up by the re-query on the next attempt — since `delete_hosts` re-evaluates `select_query.count()` at the top of its `while` loop — so they will be re-deleted and re-added to the set, naturally deduplicating. IDs from previously committed batches (successful earlier batches within the same or prior attempts) are already gone from the database and won't appear again, so they are correctly preserved in `deleted_id_set`. After the retry loop completes (either successfully or by exhausting retries), convert `deleted_id_set` to a sorted list for `deleted_id_list`. **Then** execute the tracking loop, which iterates `host_id_list` and checks membership in `deleted_id_list` — this ensures tracking reads the fully populated list including IDs from all committed batches across all attempts. On each attempt, catch both `OperationalError` and `OutboxSaveException`. For `OperationalError`, check via `is_deadlock_error(e)`. For `OutboxSaveException`, check if the underlying cause is a deadlock via `is_deadlock_error(e.__cause__)` (since `write_events_to_outbox_batch` wraps `SQLAlchemyError` in `OutboxSaveException` using `raise ... from db_error`). When the caught error is a deadlock, log a warning including the attempt number, call `db.session.rollback()` to release locks, sleep for `DEADLOCK_RETRY_DELAY` seconds, and continue to the next attempt. If all retry attempts are exhausted, log a final warning and call `flask.abort(409)` with a message indicating a concurrent operation conflict and advising the client to retry later. Re-raise non-deadlock errors unchanged on any attempt. Because the handler is inside `_delete_host_list`, it covers all three calling paths: `delete_host_by_id`, `delete_hosts_by_filter`, and `delete_all_hosts`.

- `tests/test_api_hosts_delete_by_id.py` (modify): Add a test that creates a host, then patches `api.host.delete_hosts` to raise an `OperationalError` wrapping a `psycopg2.errors.DeadlockDetected` (construct as `OperationalError("deadlock detected", params=None, orig=DeadlockDetected())`). The mock should raise on every call so that all retry attempts fail. Verify the API returns a 409 status. Model the test after the existing `test_attempt_delete_host_read_only` test which patches a dependency and asserts a non-200 response code. Import `OperationalError` from `sqlalchemy.exc` and `DeadlockDetected` from `psycopg2.errors`. Add a second test where the mock raises `OutboxSaveException` with a `DeadlockDetected`-caused `OperationalError` as its `__cause__` on every call, and verify the API also returns 409. Add a third (recovery) test where the mock raises an `OperationalError` wrapping `DeadlockDetected` on the first call but succeeds on the second call, and verify the API returns a 200 status — confirming that the retry mechanism works end-to-end. Add a fourth test (later-batch deadlock/recovery) that calls `_delete_host_list` directly (imported from `api.host`) instead of going through the REST endpoint, because `delete_host_by_id` returns `200 {}` with no count in the response body. The mock for `delete_hosts` returns a generator that yields one successful `OperationResult` and then raises a deadlock `OperationalError` — simulating a deadlock on the second batch after the first batch committed. On the retry (second call), the mock returns only the remaining host successfully. Verify that `_delete_host_list` returns **2** (reflecting both the host deleted in the first attempt's committed batch and the host deleted on the retry), confirming that accumulated IDs are preserved across retry attempts via the deduplicating set. Also mock `time.sleep` in all deadlock tests to avoid actual delays.

## Constraints
- The delete operation must be retried up to 3 times before returning a 409. Each retry should roll back the failed session and wait briefly to allow the conflicting transaction to complete.
- Non-deadlock `OperationalError` instances must still propagate as 500 errors — only DeadlockDetected should be converted to 409.
- Non-deadlock `OutboxSaveException` instances must also propagate unchanged.

## Known Limitations (out of scope for this fix)
- **Message ordering with rollback**: If a deadlock occurs after deletion events have already been published to Kafka (e.g., during a later batch's flush/commit), consumers may receive deletion events for hosts that were not actually deleted because the transaction rolled back. A full fix would require a transactional outbox pattern or post-commit message publishing, which is a larger architectural change. This should be tracked as a follow-up item.
- **Partial batch deletion on exhausted retries**: When `delete_hosts` processes hosts in batches and a later batch deadlocks after earlier batches have already committed, and all retry attempts are exhausted, the 409 response does not report which hosts were successfully deleted in the committed batches. The `deleted_id_set` preserves the IDs (including some from rolled-back batches), but since all retries failed, the response is a 409 without a detailed breakdown. A subsequent retry of the same ID list by the client may fail `check_all_ids_found` for already-deleted hosts. Returning partial progress in the 409 response body should be tracked as a follow-up item.
